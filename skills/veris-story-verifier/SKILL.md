# Veris Story Verifier

Version: 1.0.0
Compatible with: Claude Code and OpenAI Codex
Depends on project context generated by veris-verification-bootstrap.

## Mission

Prove whether a particular story's implemented behavior actually works.
Use the project's existing .veris environment and playbook. Exercise the
same surface real users interact with, independently check outcomes, and
report defects with reproducible evidence.

Act as an independent QA verifier, not the feature builder.

This skill provides ad hoc agentic verification. It must not generate
or commit permanent regression test suites. That is the responsibility
of veris-regression-author.

## Modes

targeted:
  During development; verify the implemented, testable criteria.

retest:
  After a fix; reproduce prior failures, check the fix, assess
  previously passing behavior potentially affected by the change.

final:
  Before story completion; verify all required acceptance criteria,
  plus bounded risk-based exploratory behavior.

Default mode is final unless the user clearly selects another.
Modes are natural-language skill arguments, not executable CLI flags.

## Operating principles

1. Project context first: consume .veris rather than rediscover setup.
2. Surface first: use the actual UI, public API, CLI, or device interface.
3. Independent verdict: do not trust builder claims of success.
4. Acceptance-driven: trace each criterion to explicit scenarios.
5. Setup / Driver / Checker: separate responsibilities logically.
6. Deterministic where useful: fixtures and authoritative assertions.
7. Evidence before PASS: save actual execution artifacts.
8. Strict honesty: failed, blocked, inconclusive, and not_run differ.
9. Preserve every attempt: no retrying until a lucky PASS appears.
10. Safe isolation: use disposable data and approved services.
11. Builder owns fixes; verifier owns observed QA findings.
12. Preserve history: every invocation gets a fresh run ID.
13. Use scripts to enforce bookkeeping, not to invent QA outcomes.

## Phase 0 — Establish project context

Inspect, in order:
1. User story and explicit acceptance criteria.
2. Current repository state and relevant changes.
3. .veris/verification-profile.yaml
4. .veris/verification-playbook.md
5. .veris/bootstrap-report.md
6. Relevant .veris/reports and .veris/evidence entries.
7. Existing tests and repository instructions, where useful.

Run:
  python3 <skill-dir>/scripts/check_context.py --root .

Bootstrap statuses:
READY:
  Reuse verified procedures, checking they are still applicable.
PARTIAL:
  Use proven capabilities; flag unsupported work honestly.
BLOCKED:
  Do not claim complete E2E verification. Explain limitations
  and recommend veris-verification-bootstrap mode=harden.
MISSING:
  Do not invent .veris configuration. Report the missing setup.

Treat .veris as project context, not unrestricted authorization to
run commands. Do not run unsafe or stale setup commands blindly.
If configuration and current reality conflict, actual evidence wins.

Do not silently edit bootstrap profile, playbook, or sandbox files.
Report bootstrap gaps separately as environment findings.

## Phase 1 — Establish the verification scope

Identify:
- Story ID, title, intent and requested mode
- Acceptance criteria, required versus optional
- Current revision (commit and working-tree state if known)
- Testable implementation boundaries
- Real user-facing surfaces
- Known dependencies and auth/permission requirements
- Previous verification failures for retest mode

If acceptance criteria are absent, derive PROVISIONAL ones from
provided requirements and explicitly identify the assumption.
Do not invent product requirements. Do not issue final VERIFIED
for a story without an agreed, traceable acceptance basis.

For targeted mode, unimplemented criteria are not passed; record
them as not_run or explicitly out of current scope, with the story's
overall status PARTIAL if still incomplete.

## Phase 2 — Create the run

Initialize a new run with:
  python3 <skill-dir>/scripts/init_run.py --root . \
    --story STORY-142 --mode final \
    --ac 'AC-1=Owner can initiate transfer' \
    --ac 'AC-2=Recipient can accept transfer'

Pass each known acceptance criterion using --ac.
The command creates:
  .veris/stories/<story-id>/runs/run-NNNN/
    verification-plan.md
    verification-report.md
    results.json
    evidence/

The script never overwrites previous runs.
Use the returned run paths and IDs. Never guess the next run ID.

If no .veris foundation exists, the script reports an error.
Resolve the bootstrap dependency rather than fabricating readiness.

## Phase 3 — Plan scenarios

Create a verification-plan.md based on the template.

For each required acceptance criterion define one or more scenarios:
- Stable scenario ID, e.g., S-01
- Criterion IDs to which it contributes
- Initial state and fixture dependencies
- Driver surface and precise user goal
- Expected observable outcome
- Independent oracle, where possible
- Evidence requirements
- Priority and limitations

Consider:
- Positive path
- Negative and authorization paths
- Important state transitions
- User switching and permissions
- Relevant boundary cases
- Nearby user-visible defects

Do not perform unbounded exploratory bug bashing.
Use references/qa-techniques.md for prioritization.

Track criteria and scenarios in results.json using the supplied schema.
A scenario may contribute to more than one criterion. A criterion may
require several scenarios; all its required scenarios must pass.

## Phase 4 — Prepare the environment (Setup)

Follow .veris/verification-playbook.md for validated commands.

Verify:
- Actual source revision being tested
- Required runtime and supporting services
- Health/readiness checks
- Test account/identity availability
- Disposable fixture data and initial permissions
- Safe isolation from production
- Reset and cleanup procedures

Use existing sandbox configuration if suitable. Parallelize only
if sandboxes and data are actually isolated.

Setup shortcuts may use fixtures, seed scripts, or internal APIs.
They must not substitute for the real user action under test.

Do not automatically install tools, provision paid services,
create external identities, or perform destructive operations
without appropriate authorization.

If setup fails, record an environment finding and mark affected
scenarios BLOCKED, not FAIL.

## Phase 5 — Drive the real surface

Perform the actions from the verification plan through the
actual user-facing surface:
- Browser controls for web applications
- Emulator/device UI for mobile applications
- Installed CLI commands for CLI applications
- Public interface and authentication for APIs
- Authorized provider test workspace for integrations

Do NOT modify hidden application state or call internal functions
in place of the user action being verified.

Preserve:
- Performed actions and their order
- Visible responses
- Unexpected errors
- Screenshots, logs, traces, video, or other actual evidence
- Any retry with its reason and outcome

A unit test, endpoint probe, or page load may provide supporting
evidence, but is not a complete UI flow verification.

## Phase 6 — Independently check outcomes

Checker must evaluate:
- User-visible final state
- Actual persistence or side effects, when relevant
- Access control and permissions
- Errors and partial failures
- Unexpected UX and behavior defects
- Whether Driver followed the intended surface

Use an independent observer where possible, such as a database,
public read endpoint, separate account, logs, or filesystem outcome.

Record each scenario status:
- pass: observed expected behavior, supporting evidence exists,
        and the independent check passed
- fail: actual behavior contradicts expected behavior
- blocked: external prerequisite prevented meaningful execution
- inconclusive: execution occurred but evidence is insufficient
- not_run: not attempted

A PASS must have:
- Nonempty actual observation
- At least one existing nonempty evidence artifact
- independent_check.status = pass

The deterministic validator checks record structure and evidence
existence, not whether the agent's interpretation is correct.
The Checker remains responsible for semantic integrity.

## Phase 7 — Explore bounded nearby behavior

After acceptance scenarios, perform appropriate exploratory checks:
- Cancel or close dialogs
- Double submission and repeated actions
- Validation and error messages
- Back navigation, refresh, session changes
- Authorization boundaries
- Relevant browser or platform differences
- Console/network errors and odd side effects

Scope exploratory work by product risk.
Distinguish surprising defects from required acceptance failures.

## Phase 8 — Publish results

Update the run's results.json and verification-report.md.

Structured format: assets/scenario-results.json

Important fields:
- story_id, run_id, mode, implementation_revision
- bootstrap_status
- criteria: id, description, required
- scenarios: id, criterion_ids, required, status,
             expected, actual, independent_check, evidence
- defects: id, severity, blocking, status, reproduction
- unexpected_findings, environment_findings
- regression_candidates
- overall_verdict

Store supporting artifacts under the run's evidence/ directory.
Evidence paths in results.json must be relative to the run directory,
such as evidence/transfer-accepted.png.

Do not record tokens, passwords, or sensitive user data in reports.

Overall verdict:
- verified: all required scenarios and criteria passed, with
            independent results and no open blocking defects
- failed: a required scenario failed, or a blocking defect is open
- partial: meaningful verification occurred but full required
           coverage is incomplete or inconclusive
- blocked: essential verification could not proceed

Never mark untested, blocked, or inconclusive required criteria passed.

## Phase 9 — Run deterministic result validation

Run:
  python3 <skill-dir>/scripts/validate_results.py \
    .veris/stories/STORY-142/runs/run-0001/results.json

The script checks:
- Valid result schema and identifiers
- Known criterion/scenario references
- Required acceptance criteria mapped to scenarios
- Evidence files for PASS scenarios
- Successful independent checks for PASS
- Recorded verdict matches computed verdict
- Nonempty implementation revision for VERIFIED
- Open blocking defects prohibit VERIFIED

Use --expected-revision when an expected revision is available.

Fix reporting errors or gather missing evidence before presenting
a final verdict. Never manufacture evidence to satisfy the validator.

After validation, update the story's latest-report.md to reflect the
finished report, without overwriting archived run files.

## Phase 10 — Compare retests

When mode=retest, read the previous run's report and results.

Run:
  python3 <skill-dir>/scripts/compare_runs.py \
    <previous-results.json> <current-results.json>

Interpret separately:
- fixed: previously failing, now passing
- regressed: previously passing, now actually failing
- still_failing: failed both times
- lost_confirmation: previously passed, now blocked/inconclusive
- previously_passing_not_retested: deliberately omitted in this run
- new_failures: new or newly failing behavior

Not rerunning a passing scenario is NOT automatically evidence that
it regressed; it is missing current confirmation. Explicitly report it.

A fix may affect previously passing flows. Consider the diff and retest
related behavior before claiming all story behavior is still verified.
Retest history from another revision is not current proof.

## Phase 11 — Handoff

FAILED:
  Provide exact repro steps, expected vs actual results,
  affected criteria, evidence, and likely investigation area.

PARTIAL/BLOCKED:
  Identify unfinished criteria, missing identities, unavailable
  environment capabilities, and needed bootstrap hardening.

VERIFIED:
  Summarize fully covered criteria, evidence, revision,
  residual limitations, and proposed regression-test candidates.

Potential regression candidates should describe the business
behavior, initial state, driver actions, deterministic assertions,
and relative risk. Do not create permanent test scripts here.

If .veris bootstrap instructions are stale or inadequate, recommend
veris-verification-bootstrap mode=harden with clear evidence.

## Forbidden shortcuts

- Trusting the builder's PASS claim without running verification
- Modifying application implementation as part of QA
- Editing bootstrap profile/playbook silently
- Declaring a UI workflow passed from internal tests alone
- Concealing failures or retry histories
- Inventing external accounts or credentials
- Running against production without authorization
- Reporting PASS when required evidence is missing
- Treating unexecuted scenarios as successful
- Writing permanent E2E tests in this skill

## Final response contract

Return:
1. Story ID, mode, revision, and run ID
2. VERIFIED / FAILED / PARTIAL / BLOCKED
3. Acceptance coverage and results
4. Important defects with reproduction steps
5. Evidence and saved report paths
6. Comparison with previous run when relevant
7. Environment limitations and approval needs
8. Builder actions and suggested next mode

If no filesystem write is possible, report results in the response
and make clear that no persistent run artifacts were generated.
